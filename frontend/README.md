# Summerfield HQ MVP

React and TypeScript frontend for department tasks and updates. It uses the same Supabase accounts, organization membership, and department assignments as the Streamlit app. The interface is responsive and has no Claude dependency.

## Design rebuild

The dashboard, shared navigation, and department pages now follow the visual design in `../docs/design/reference/Summerfield HQ.html`. The original file is a design reference, not runtime code. In local development, use **Preview the new HQ design** on the sign-in screen, or **Design preview** in a signed-in workspace, to inspect these screens without writing data. The unauthenticated preview is removed from production builds; signed-in production preview is limited to admins. Preview mode displays all reference departments but cannot read or change company records; normal signed-in views still honor assigned department access.

Every section in the prototype's main sidebar now has a React screen. This is a UI-first conversion, not a claim that every underlying service is connected. Calendar, projects, meeting notes, SOP drafts, Drive links, email, notifications, and access administration still need their shared-data integrations. Local preferences such as the chosen department, hidden dashboard cards, and dismissed tour are saved in this browser.

The Departments index at `#/departments` is also available in both signed-in and Design preview modes. Preview lists the reference departments; signed-in mode lists only assigned departments and their real open-task counts.

The next rebuilt screen is **Team Calendar** at `#/calendar`. It includes month/list views, department visibility filters, keyboard-accessible days and events, and a centered event dialog. In design preview, create, edit, and delete temporary all-day or timed events, choose colours, and set weekly, biweekly, monthly, or custom interval repeats. A repeat edit/delete applies to the whole series. Events remain in memory across navigation but clear on reload or exit from preview. Normal signed-in mode has no calendar records or write controls until its API is connected. PDF and Print both open the browser print dialog; PDF uses the browser's Save as PDF destination. Google Calendar, invitations, store-location records, and per-occurrence recurrence exceptions remain disconnected.

Click a date number or the empty space in a month cell to open New event with that date selected. The dialog follows Vy's screenshot: paired calendar/location fields, all-day toggle, colour swatches, optional end date, repeats, team invitation disclosure, where, and notes. A blank end means the start day, including timed events. Location offers company-wide or a manually named preview location; no live store list is queried. Team selections are retained with the temporary event but send nothing. The people picker is explicitly unavailable until its directory is connected. Mobile fields stack and the form scrolls without hiding Save/Cancel.

The calendar module is lazy-loaded and uses FullCalendar 6 with its RRule integration rather than custom recurrence expansion. Run its focused date/validation tests with Node 22.18+ or Node 24: `npm test`.

**Department folders** at `#/folders` now uses the prototype's department grid and the same folder card as each department dashboard. Preview shows the reference departments; signed-in mode lists the account's assigned departments plus the company-wide reference card. Dashboard links appear only for departments the current mode can open. Folder names are reference content, not live Drive records; Drive links, uploads, and shared-file actions remain disconnected and their controls are disabled.

**How HQ works** at `#/help` now has current-workflow guides, first-day links, and a five-step front-end tour. The dashboard's tour button opens this same tour. It links only to routes that exist and calls out calendar and Drive features that still need connections. Tour completion is a browser-only preference; the guides do not fetch company data or write to Supabase.

**Market watch** at `#/watch` has briefing, alert inbox, saved-item, and learning views. The design preview includes sample alerts and temporary saved items. Email alerts, shared storage, and analysis are not connected in signed-in mode.

**Who to ask** at `#/ask` and **Decision chart** at `#/decisions` now share a feature module for ownership areas, contact profiles, and decision rules. Design preview includes clearly labeled sample people and records, searchable ownership routing, a team directory, decision-limit answers, and temporary add/edit/remove forms. These edits stay in memory across navigation and disappear on reload. Signed-in views do not show sample assignments or claim that live decision authority is known; the ownership/directory API and ticket/approval routing remain disconnected.

**Projects** at `#/projects` and `#/project/:id` has a dashboard, filters, progress cards, a ticket-desk entry point, and project Tasks, Chat, Files, and Details views. Design preview uses sample projects and memory-only project, task, ticket, and message edits. These clear on reload. Signed-in mode shows real HQ task totals where available but no invented shared projects; project storage, chat, files, and Asana synchronization are not connected.

**Ticket desk** at `#/tickets` connects to the inventory app's store-ticket RPCs. Admins and store managers with active store access can submit a ticket; the reporter, the department lead, and organization admins can read it. Authorized reviewers can follow the server's legal status transitions and assign an active department teammate, with optimistic revision checks and an activity log. The queue filters by status, department, and accessible store and shows at most 200 priority-ordered rows per filter; narrow filters when it reaches the cap. Store names are shown when the account has store access, otherwise the ID prefix is shown. Photos, project links, chat, and notifications are not connected. The inventory-owned `202609210001_tickets.sql` migration must be present in the target database; if it is missing, HQ shows a setup error rather than sample tickets. No new SQL migration was added for this UI slice.

**Learning** at `#/learn` and `#/lesson/:id` has a lesson library, team filter, search, reader, takeaways, and quick-check quizzes. Design preview uses labeled sample lessons and memory-only reading progress, scores, and manually written preview drafts. Everything clears on reload. Signed-in mode does not show sample lessons or pretend to publish: shared lesson storage, progress, and AI-assisted writing are not connected.

**Time clock** at `#/time` has half-month period views, a shift table, live clock, break actions, and correction requests. Design preview uses labeled sample records and temporary punches/requests; it cannot export payroll or send anything to HR. Signed-in timekeeping controls are disabled until an audited service and permission contract exist. The screen does not calculate payroll or determine compliance.

**Team reports** opens the current monthly board from signed-in navigation; its unframed toolbar switches weekly/monthly periods and links to the library at `#/reports`. The library provides signed-in history across weekly and monthly periods, with Drafts, Submitted, and All views, visible-name/summary/date search, filters, and cursor pagination. Search matches the displayed department/store name, summary, period, and updated date; date matching requires inventory migration `202609250004` and degrades to name/summary search with a notice until it is applied. The history library and current-period board read only report metadata from `team_reports` under RLS; opening a report loads its full payload for that exact period and store. There is one evolving report per organization, department, type, period, and optional store; submission snapshots are revisions of that report, not separate history rows. The detail page at `#/report/:department/:type/:period` connects to the existing report RPCs. Weeks run Sunday through Saturday in the Los Angeles business timezone; months use calendar bounds. Store Manager reports are per accessible store. Version-one native payloads can be edited and saved with optimistic revision checks; leads and admins can submit, and only admins can reopen. Version-two inventory-form payloads have a structured read-only weekly/monthly reader for named answers, repeatable rows, and metrics; editing remains in inventory because older positional controls cannot be safely round-tripped in HQ. Unknown versions are never overwritten. The metric catalog snapshot in `src/features/reports/metrics-v1.json` comes from `../../inventory-app/data/team_report_templates.py` via `scripts/sync-report-metrics.py` and should be refreshed only after reviewing template changes. Design preview remains a separate monthly-only, memory-only editor with sample records, presentation, and preview CSV. AI summaries, report-to-task conversion, PDF output, and vendor-pricing reports are not connected in HQ.

**Meetings** at `#/meetings` has searchable records, agenda and decision notes, an action-item summary, and a meeting editor. Design preview records and edits stay in memory. Action items do not create HQ tasks, and Drive import, email recap, and AI answers remain disabled until their integrations exist. Signed-in views show no sample company records.

**SOP Studio** at `#/sop` has a manual house-format editor, completeness checks, a preview draft library, text copy, and preview-only ready/filed states. Pasted raw notes remain visible beside the draft but are not rewritten by AI. File import, Word generation, live draft storage, approval, and Drive upload are not connected. Signed-in views show no sample drafts or write controls.

**Locations** at `#/locations` and `#/location/:id` has searchable store files, overview facts, equipment, linked build-out work, folder links, and a history tab. The Design preview holds sample locations and temporary edits in memory; equipment CSV and browser print work locally. Shared location storage, catalog synchronization, file attachments, calendar events, audits, and live build-out links are not connected. Signed-in views show no sample company locations.

**Master equipment catalog** at `#/catalog` has equipment, smallwares, supplies, vendors, standards, and recent changes. The Design preview has sample records, temporary edits, category/search filters, and a downloadable order-request CSV; it does not send orders or synchronize to location files. Signed-in mode shows no sample inventory. Excel import, shared catalog storage, and vendor data integration are not connected.

**People & access** at `#/people` shows the prototype roster, role selector, department visibility, details, and access requests in Design preview only. All edits are memory-only examples and do not grant or revoke access. Signed-in admins see their actual organization role and visible departments in a read-only view; non-admins cannot open the page. The real organization membership and department assignment flows remain in Team Access.

The sign-in and access-check screens use Vy's striped layout and the shared Sunny character rig, with a gentle wing wave behind the body. Unlike the HTML prototype's device PIN, HQ authenticates through Supabase Auth. It reads the existing `organization_memberships` and `team_report_memberships` roles from the inventory app; Team Access remains the place to change an account's department assignments. No role can be chosen on the login form.

In the workspace, click Sunny for a joke or encouraging thought and three floating hearts. Drag her up and release to drop her to the bottom of the visible workspace, above the mobile navigation. The browser animates an accelerating fall with flapping wings, tucked feet, and a soft landing; catching her mid-fall preserves her current position. Hiding her, resizing the viewport, or leaving the workspace cancels the fall. The shared `SunnyCharacter` renderer uses the original artwork with separate wing, foot, body, and expression layers. Wings sit in front of the torso, as in the artwork, and lift cleanly because the body layer has no wing baked into it. Both feet alternate while dragging, and expressions never replace the limbs. Horizontal movement uses a steady directional lean; upward movement uses the back view. Click reactions keep the 820ms, 38px jump with independent wing flaps. Dragging uses direct transform positioning with a fixed step cadence and a direction threshold to avoid jitter. Silhouette-masked lighting and a contact shadow add depth without a 3D runtime. After 90 seconds without interacting with Sunny, she sleeps with slow breathing and drifting Zs; clicking or dragging wakes her. The lower-left Sunny switch and her landed position are saved in this browser. Reduced-motion settings skip the fall, disable character animations, and show static hearts briefly.

Sunny's face is drawn live over the original artwork. Her eyes follow the pointer and blink, the lids and pupils change for happy, wink, surprised, dizzy, drowsy, and sleeping faces, and her beak opens while her lines type out. Vy's heart, glasses, and teary faces are still used for their lines. The dragonfly is a separate layer (`body.webp`, `wing.webp`, and `fly.webp` are generated from `front.webp` by `scripts/split_sunny_layers.py`), so it hovers, lags behind her jumps, and sometimes takes a lap around her head. While she is idle she glances around, tilts her head, stretches, or hops. Rubbing her back and forth with the mouse pets her. She dangles and swings while dragged, and a hard shake leaves her dizzy when she lands. After 35 quiet seconds she may ask for boba (at most once every four minutes); clicking her then gives her a sip. She yawns 9 seconds before napping. She greets you once per browser session.

The sparkle button beside Sunny (visible on hover or keyboard focus, and always on touch screens) opens Vy's **Play with Sunny** menu. It has five items: give her a boba, let the dragonfly fly, a wiggle dance, a hug, and nap time (or wake up). Clicking the dragonfly on her head also sends it for a lap. Only one performance runs at a time: starting another, clicking her, or grabbing her ends the current one cleanly. Her line comes after the move, so the speech bubble never covers it. A second boba within a minute gets a polite "still full" instead of another sip. The menu opens toward the side with more room, stays on screen on phones, works with the arrow keys, and closes with Escape. With reduced motion, actions keep their words and faces but drop the movement.

## Included workflows

- Sign in and sign out with an existing Summerfield Supabase account.
- See only departments assigned to the account; company admins can see every department.
- Read tasks and updates for accessible departments.
- Create department tasks, set a due date, and assign an active department teammate.
- Complete or reopen a task as its creator, assignee, or department lead.
- See **My tasks** (`#/tasks`), rebuilt from Vy's design: your tasks grouped as Overdue, Today, This week, Later, and Done (last 15), plus the open tasks you asked others to do. **New task** can go to any department you can write to, and defaults to you. **Open** shows a task's details, with done or reopen. Projects, priority, status, start dates, locations, files, comments, and the weekly email digest aren't stored by HQ yet, so they aren't shown. The email buttons are visible but disabled.
- Post a department update as a member or lead.
- Switch organizations if the account belongs to more than one.

The database enforces department access with Row Level Security and the `set_hq_task_status` function. The browser uses only the Supabase publishable key. No service role key belongs in the frontend.

## Run locally

1. Apply `../backend/supabase/migrations/202609220001_hq_mvp.sql` to the target Supabase environment after the existing Summerfield schema migrations.
2. In this folder, copy `.env.example` to `.env.local` and set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` for that environment. The key is public; do not place database passwords or service role keys here.
3. Run `npm install` and `npm run dev`.
4. Sign in with an account already assigned to the organization. Department membership is managed through the existing Team Access page.

Run `npm run build` for a production bundle in `dist/`. The app uses hash routes, so a static host can serve the bundle without route rewrites. Configure the two `VITE_` variables in the build environment.

## Scope

Connected workflows now include HQ tasks, team updates, version-one weekly/monthly Team Reports, and store tickets where their shared migrations are applied. The other prototype sections are UI-first previews until their shared services are integrated; this React app does not yet replace the full inventory report form, inventory, calendar, or department tools.
